# x86_64

The `x86_64` profile has a native ring-3 execution backend, in addition to the
architecture-neutral model tests.

## Boot and platform

- `boot16.S` is the shared i386/x86_64 BIOS sector. It loads a fixed 4 MiB
  payload using a 16 KiB low-memory bounce buffer and protected-mode copies
  into high memory; it does not load through VGA, EBDA or BIOS memory.
- `boot.S` enters long mode, establishes supervisor identity mappings and the
  bootstrap stack, clears `.bss` and enters the kernel.
- `linker.ld` supplies the freestanding kernel layout.
- `ops.cpp` provides statically selected architecture instructions.

## Native execution

`execution.cpp` and `execution.S` implement `ok::arch::execution`:

- Four-level CR3 address spaces with 4 KiB user pages in
  `[0x40000000, 0x80000000)`. Kernel identity leaves remain supervisor-only.
- User read-only/NX enforcement, CR0.WP and rejection of writable executable
  mappings, invalid ranges and duplicate pages.
- GDT user descriptors, TSS kernel stack, double-fault IST, exception/IRQ IDT,
  SYSCALL MSRs and safe `iretq` return to ring 3. SYSCALL switches to a
  kernel-owned stack before accessing memory through the stack pointer.
- Full general-register and x87/SSE state preservation, user FS/GS bases and
  kernel context restoration before compiled trap handling.
- PIT/PIC timer IRQ 32, allowing a non-cooperative user loop to be preempted.
- Synchronous return to the original kernel stack on real syscall, timer or
  fault. Generic runtime code owns scheduling, syscall policy and process exit.
- Per-page user-copy checks and generation-checked address-space handles.

The backend supports one executing CPU and 16 address spaces, each with up
to 16 sparse user page tables. Application backing pages belong to the
caller's reserved physical storage below 1 GiB; the backend owns page tables
only. AVX, AP startup, hardware SMP scheduling, x2APIC interrupt delivery and
general physical-page allocation remain future work. This is a native
mechanism, not a claim of complete POSIX conformance.

## Hardware acceptance test

From the kernel repository:

```sh
python3 scripts/test_native_x86_64.py --toolchain ../SysToolchain/build/local-sdk-x86_64
python3 scripts/test_native_x86_64.py --toolchain ../SysToolchain/build/local-sdk-x86_64 --poison-bootstrap-tables --output build/native-tests/x86_64-poisoned
```

The standalone test builds independently of xmake configuration and runs
actual ring-3 instructions in QEMU. It checks CPL3/SYSCALL registers, SSE
preservation, distinct physical backing at the same virtual address, timer
preemption, supervisor isolation, read-only/NX/unmapped faults, invalid
instructions, user-copy bounds and kernel CR3 restoration. Successful runs
emit `OK_NATIVE_TEST_PASS scope=hardware architecture=x86_64`; the serial log
is `build/native-tests/x86_64/serial.log`. The same test exercises the BIOS
bounce loader with the full 4 MiB padded payload.
The second invocation fills all bootstrap page tables with nonzero bytes after
BIOS loading and before production initialization, so paging cannot depend on
QEMU's initially zeroed RAM or the boot payload's padding.

`xmake qemu-test` separately validates the standalone debug kernel, while the
OS integration tests validate applications linked against the exported SDK.
Metadata model tests do not substitute for either execution path.
